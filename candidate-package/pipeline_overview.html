Triage & Resolve — System Reference

Triage Pipeline Flow

One request in, one audit record out. The pipeline sends language judgment to an LLM and keeps every hard constraint — the approval gate, tier consequences, purchase bands, PII handling — in plain code. This page is the map: the stage sequence, where requests exit early, how the human gate and tool failures are handled, and how the eval harness scores it.

01

The pipeline

Eight stages. Stages 01–05 are the judgment path and run inside one try / except — any failure there degrades to ESCALATE, it never crashes the batch. Stages 06–08 always run, even for a request that was rejected upstream.

  • LLM call
  • deterministic code
  • hard constraint (code)
  • early exit → REJECT
  • AUTO_RESOLVE
  • ROUTE
  • ESCALATE
  • REJECT

03

The approval gate & tool failure

Inside execute_tools, for an access_request with a resolved tier. The gate is plain control flow — grant_access is unreachable until the gate returns true — so the guarantee is inspectable at a glance rather than buried in a framework.

Why the retry budget is only 2

grant_access is a mutating, non-idempotent call. With no idempotency key, blindly retrying a call that actually succeeded upstream but lost its response would grant access twice — that risk caps the retry count more than the failure math does.

Residual failure after 2 attempts is ~2.25% (0.15²); the create_ticket fallback covers that tail safely, which a 3rd or 4th automated retry of a mutation does not. No backoff: the stub's failure is instantaneous and independent per call.

Three failure modes, three treatments

Malformed LLM JSON → gateway retries once, feeding the error back.

LLM call infra failure (timeout, 429, 5xx) → gateway backoff-retry ×3, then process_request's try/except degrades to ESCALATE.

grant_access ~15% → bounded retry then ticket, as drawn above.

04

The eval harness

python -m starter.run_evals — one command, per-dimension metrics, never one aggregate score. Three runs feed the scorers. The two probes exist so the gate and tool-failure invariants are checked deterministically every run, not only when the seeded 15% RNG happens to fire.
